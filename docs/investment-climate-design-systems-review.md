# Обзор открытых дизайн-систем для доработки страницы «Инвестиционный климат»

Дата: 01.08.2026

## Вводная

Страница «Инвестиционный климат Свердловской области» — длинный государственно-деловой аналитический одностраничник (~12 разделов, таблица 43 мероприятий с фильтрами, карточка мероприятия в drawer, режим демонстрации). Стек: Next.js + React + TypeScript + Tailwind + Framer Motion; шрифт IBM Plex Sans; светлая строгая палитра на CSS-токенах `--ic-*` (фон `#F6F7F9`, поверхности `#FFFFFF`, границы `#DDE1E7`, текст `#1A1E26`, единственный акцент `#1E4FA3`).

Цель обзора — подобрать в четырёх зрелых открытых дизайн-системах (GOV.UK Design System, USWDS, PatternFly, IBM Carbon) проверенные паттерны для задач доработки: свёртываемое боковое оглавление с подсветкой текущего раздела; компактная строка фильтров с активными метками; таблица со sticky-заголовком, компактным режимом и адаптивным скрытием столбцов; карточка мероприятия как primary-detail с 4 разделами вместо 8 вкладок; раскрывающаяся библиотека практик; различение трёх уровней контента (факт / аналитический вывод / предложение); правило «не прятать обязательный контент».

**Жёсткое ограничение:** никакие сторонние библиотеки и CSS не подключаются. Из дизайн-систем заимствуются только паттерны, правила и логика поведения; вся реализация — собственные React-компоненты на Tailwind с существующими токенами `--ic-*`. Ответ на вопрос «нужна ли зависимость» по каждой системе — **нет**.

## 1. GOV.UK Design System

Сайт: https://design-system.service.gov.uk

### Какие задачи решает система

GOV.UK Design System — эталон контентно-ориентированного государственного дизайна: минимум декора, максимум читаемости и однозначности. Её главная ценность для нас не в визуале, а в жёстко сформулированных правилах «когда использовать / когда НЕ использовать» для каждого компонента, выведенных из пользовательских исследований государственных сервисов. Для страницы, которую читают чиновники и инвесторы, это самая близкая по духу система: текст первичен, интерактив — только там, где он оправдан.

### Подходящие нам решения

- **Details** (https://design-system.service.gov.uk/components/details/) — свёртываемый блок «показать подробности». Ключевое правило: *не используйте details, чтобы скрыть информацию, которая нужна большинству пользователей*; компонент — только для вспомогательного контента, нужного части аудитории. Это прямой ответ на нашу задачу «правило не прятать обязательное»: раскрывающаяся библиотека практик и второстепенные методические пояснения — да, управленческое резюме и ключевые выводы диагностики — никогда. Документация также предупреждает: часть пользователей не кликает по ссылке-заголовку, думая, что она уведёт со страницы, — поэтому заголовок раскрытия должен явно обещать «подробности здесь же».
- **Tabs** (https://design-system.service.gov.uk/components/tabs/) — важны именно правилами «когда НЕ использовать»: вкладки не подходят, (а) если контент нужно читать последовательно (пошаговый процесс), (б) если пользователю нужно сравнивать содержимое разных вкладок — переключение и запоминание фрустрирует, (в) если вкладки используются как навигация по странице. Это обоснование нашего решения свернуть 8 вкладок карточки мероприятия до 4 смысловых разделов: содержимое карточки читается связно, а не «по ящикам».
- **Summary list** (https://design-system.service.gov.uk/components/summary-list/) — список «ключ–значение» на `<dl>` для фактических атрибутов. Идеален для «паспорта» мероприятия в карточке (срок, ответственный, статус, KPI) и для блока метаданных методики. Правило: использовать только для пар «ключ + значение», не для табличных данных.
- **Warning text** (https://design-system.service.gov.uk/components/warning-text/) — восклицательный знак + полужирный текст для предупреждения о важных последствиях. У нас — маркировка критических аналитических выводов и рисков в диагностике: то, что читатель обязан увидеть, оформляется именно так, а не прячется в details.
- **Headings / typography** (https://design-system.service.gov.uk/styles/headings/) — строгая лестница заголовков (xl → l → m → s), семантика `h1–h4` совпадает с визуальным размером, caption-подпись над заголовком (`govuk-caption-*`) для обозначения принадлежности раздела. Caption-приём хорошо ложится на наши разделы («Раздел 4 — Диагностика» серым кеглем над заголовком).

### Что НЕ подходит и почему

Брендовые элементы: чёрный header с короной, шрифт GDS Transport (лицензионно закрыт), «канцелярская» жёлтая подсветка фокуса, зелёная кнопка-CTA, общая эстетика «форма госуслуги». Наша страница — аналитический документ, а не транзакционный сервис; переносим правила, не переносим облик.

### Воспроизводимость средствами Tailwind + свои компоненты

Да, полностью. Details — нативный `<details>/<summary>` или контролируемый React-компонент с `useState` + иконка-шеврон (`border-[var(--ic-border)]`, `text-[var(--ic-accent)]` для заголовка). Summary list — `<dl>` с grid: `grid grid-cols-[max-content_1fr] gap-x-6 border-b border-[var(--ic-border)]`. Warning text — flex-строка: круглый значок «!» на нейтральном графите + `font-semibold`. Заголовочная лестница — утилиты `text-3xl/2xl/xl/lg font-semibold tracking-tight` поверх IBM Plex Sans.

### Нужна ли зависимость

Нет. GOV.UK Frontend — это npm-пакет со стилями и макросами Nunjucks, нам не нужен ни один его байт: берём только контентные правила и структуру разметки (семантичные `<dl>`, `<details>`, иерархия заголовков).

### Риск конфликта с текущим стилем

Минимальный — заимствуются правила, а не CSS. Единственный риск: warning text у GOV.UK визуально «кричит»; в нашей сдержанной палитре его стоит смягчить (графитовый значок вместо чёрного жирного, без жёлтых/красных заливок), сохранив функцию «нельзя не заметить».

### Итоговая рекомендация

Принять GOV.UK как «контентную конституцию» страницы: правила details/tabs становятся нашим внутренним правилом «не прятать обязательное», summary list — стандартом фактических блоков карточки, warning text — стандартом критических выводов, лестница заголовков — основой типографики разделов.

## 2. USWDS (U.S. Web Design System)

Сайт: https://designsystem.digital.gov

### Какие задачи решает система

USWDS — федеральная дизайн-система США для информационно насыщенных государственных сайтов. В отличие от GOV.UK, она сильна именно в компонентах для длинных контентных страниц и больших таблиц данных: внутристраничная навигация, боковые меню, богатый набор табличных вариантов. Доступность (Section 508 / WCAG 2.1 AA) встроена в каждый компонент.

### Подходящие нам решения

- **In-page navigation** (https://designsystem.digital.gov/components/in-page-navigation/) — прямое решение задачи бокового оглавления. Паттерн: сайдбар генерируется из заголовков `h2/h3` основного контента, остаётся sticky при прокрутке, а текущий раздел подсвечивается через **Intersection Observer** (scroll spy). Рекомендация USWDS: применять на страницах длиннее ~3 экранов со структурированными заголовками — наша страница на 12 разделов подходит идеально. Важная деталь доступности: ссылки навигации идут в tab-порядке до основного контента, при переходе фокус ставится на целевой раздел.
- **Side navigation** (https://designsystem.digital.gov/components/side-navigation/) — иерархическое вертикальное меню до трёх уровней с состоянием «active» («показывайте пользователю, где он находится в иерархии»). Полезно как модель двухуровневого оглавления (раздел → подраздел) и как источник предупреждения: слишком длинный список — пользователи не заметят нижние пункты. Для 12 разделов держим один уровень + подпункты только у крупных разделов, плюс режим сворачивания в узкую полосу.
- **Table** (https://designsystem.digital.gov/components/table/) — самый полный «государственный» набор табличных вариантов: `usa-table--sticky-header` (шапка закреплена при прокрутке), `usa-table--compact` (плотный режим), scrollable-контейнер для широких таблиц, сортировка через `data-sortable`, полосатая заливка для читаемости длинных строк, и **stacked-вариант** — на узких экранах строки складываются в карточки, а имя столбца выводится через `data-label`. Для таблицы 43 мероприятий берём связку sticky header + compact + сортировка; stacked-приём — запасной для мобильного представления.

### Что НЕ подходит и почему

Визуальный язык USWDS: фирменные синие (#005ea2), Public Sans / Merriweather, «флаговый» government banner, крупные жирные компоненты форм. Также не нужен их JS-рантайм (uswds.js) — поведение in-page nav и сортировки проще и надёжнее написать самим на React.

### Воспроизводимость средствами Tailwind + свои компоненты

Да. Scroll spy — хук `useActiveSection` на `IntersectionObserver` (rootMargin вида `-20% 0px -70% 0px`, активный id в состоянии) + `<nav>` c `sticky top-*`, активный пункт — `border-l-2 border-[var(--ic-accent)] text-[var(--ic-accent)] font-medium`. Sticky-шапка таблицы — `thead` c `sticky top-0 z-10 bg-[var(--ic-surface)]` внутри контейнера `overflow-auto max-h-*`. Компактный режим — переключение `py-3 → py-1.5 text-sm` через проп `density`. Скрытие второстепенных столбцов на средних разрешениях — `hidden xl:table-cell` на `<th>/<td>` (аналог идеи stacked: на узких экранах показываем только главное).

### Нужна ли зависимость

Нет. Берём архитектуру паттернов (scroll spy, sticky, stacked, active state); IntersectionObserver и position: sticky — нативные возможности платформы, React-обвязка тривиальна.

### Риск конфликта с текущим стилем

Низкий. Единственный тонкий момент — полосатая заливка строк: в палитре `--ic-*` использовать не серые полосы USWDS, а полутон фона (`#F6F7F9` на белом) либо отказаться от полос в пользу разделительных линий `#DDE1E7`, чтобы не утяжелять строгую поверхность.

### Итоговая рекомендация

USWDS — главный донор для двух задач: боковое оглавление (in-page navigation со scroll spy и sticky) и таблица 43 (sticky header + compact + сортировка + адаптивное сокращение столбцов). Реализуем один-в-один по логике, полностью в своей палитре.

## 3. PatternFly (Red Hat)

Сайт: https://www.patternfly.org

### Какие задачи решает система

PatternFly — дизайн-система Red Hat для сложных enterprise-приложений: консолей управления, дашбордов, больших списков объектов. Её сила — проработанные паттерны взаимодействия «список → объект → детали»: primary-detail, drawer, drilldown, плотные таблицы. Это ближе всего к нашей связке «таблица 43 мероприятий → карточка мероприятия».

### Подходящие нам решения

- **Primary-detail** (https://www.patternfly.org/patterns/primary-detail, гайдлайны: https://www.patternfly.org/patterns/primary-detail/design-guidelines) — паттерн «выбираемый список слева + панель деталей справа», предназначенный именно «для просмотра деталей элемента большого списка на той же странице» без потери контекста. Ключевые правила: выбранный элемент списка обязан иметь выраженное selected-состояние; панель деталей — drawer с крестиком закрытия; ширины панелей варьируются под контент; на мобильном drawer выезжает справа и перекрывает список на всю ширину, возврат — через постоянную шапку. Это в точности наша карточка мероприятия: drawer при выбранной строке таблицы, prev/next для соседних мероприятий, и — наше расширение паттерна — сохранение выбранного из 4 разделов при переключении prev/next (состояние раздела живёт в родителе drawer, а не сбрасывается с элементом).
- **Navigation, vertical + expandable** (https://www.patternfly.org/components/navigation) — вертикальная навигация с раскрывающимися/сворачивающимися группами, до трёх уровней вложенности, текущий пункт выделяется акцентной полосой и фоном. Модель для свёртываемого бокового оглавления: expandable-группы для крупных разделов, docked/компактный режим — прообраз нашего «свёрнутого в полоску» оглавления.
- **Table, compact + sticky** (https://www.patternfly.org/components/table) — вариант `compact` с уменьшенными отступами для плотных данных; sticky header через пару контейнеров скролла (Outer/InnerScrollContainer — по сути `overflow`-обёртка, что подтверждает наш CSS-подход); сортировка колонок; expandable rows для раскрытия деталей прямо в строке; `dataLabel` на ячейках для мобильного режима «колонка-в-строку». Expandable row — альтернативный (запасной) способ показа краткой сводки мероприятия без открытия drawer.
- **Drilldown-навигация** (в составе Navigation/Menu) — переход «внутрь» пункта с хлебной крошкой возврата. Полезна как модель для режима демонстрации и для перехода «мероприятие → связанная практика → назад», где важен явный и предсказуемый возврат на прежнее место списка.

### Что НЕ подходит и почему

Эстетика тёмных консолей Red Hat (тёмная вертикальная навигация, фирменный красный, шрифт Red Hat Display/Text), «приложенческий» хром (masthead, page layout), а также избыточные для читаемой страницы механики — checkbox-выбор строк, батч-операции: у нас таблица для чтения и анализа, а не для администрирования объектов.

### Воспроизводимость средствами Tailwind + свои компоненты

Да. Primary-detail — уже существующий drawer доводим до паттерна: `aside` c `fixed inset-y-0 right-0 w-[min(560px,100vw)]`, transition через Framer Motion, `selected`-строка таблицы — `bg-[var(--ic-accent)]/5 border-l-2 border-[var(--ic-accent)]`; состояние `activeSection` (один из 4 разделов) хранится в компоненте-родителе и переживает смену `selectedId` при prev/next. Collapsible-навигация — `useState` + анимация высоты; expandable row — условный `<tr>` с `colSpan`. Sticky — тот же CSS, что и в USWDS-варианте.

### Нужна ли зависимость

Нет. PatternFly-react тянет свой CSS-фреймворк и десятки компонентов — нам нужна только схема поведения primary-detail и правила состояний, которые описаны в открытых гайдлайнах и воспроизводятся ~100 строками своего кода.

### Риск конфликта с текущим стилем

Средний, если копировать визуально (тёмные панели, плотный enterprise-хром) — поэтому не копируем. При переносе только поведения риск нулевой: drawer, selected-состояние и collapsible-группы рисуются целиком в токенах `--ic-*` на белых поверхностях.

### Итоговая рекомендация

PatternFly — донор поведения связки «таблица → карточка»: правила primary-detail (selected-состояние, drawer, мобильный оверлей, сохранение контекста) плюс модель collapsible-навигации. Берём interaction-логику, полностью отвязав её от визуального языка Red Hat.

## 4. IBM Carbon Design System

Сайт: https://carbondesignsystem.com

### Какие задачи решает система

Carbon — дизайн-система IBM для data-heavy продуктов: аналитика, облачные консоли, работа с большими таблицами и фильтрами. Для нас она вдвойне релевантна: во-первых, лучший из четырёх систем проработанный паттерн фильтрации и табличный toolbar; во-вторых, Carbon построен на IBM Plex — нашем шрифте, то есть типографические пропорции системы (кегли, межстрочные, плотности строк) переносятся почти без адаптации.

### Подходящие нам решения

- **Filtering pattern** (https://carbondesignsystem.com/patterns/filtering/) — систематизация всего, что нужно нашей строке фильтров: одиночный выбор (dropdown), множественный (multiselect с чекбоксами), несколько категорий; **batch-фильтрация** (набрал условия → кнопка «Применить») против **instant** (результат обновляется после каждого клика) — для клиентской таблицы на 43 строки правильно instant. Ключевые правила: если фильтры спрятаны (в панели «Все фильтры»), на её закрытом состоянии обязан быть **индикатор-счётчик применённых фильтров**; у каждой категории и у набора в целом должен быть **сброс одним действием**; применённые значения показываются как удаляемые метки. Это дословно наша задача «поиск + 2–3 главных фильтра + „Все фильтры" + активные метки с × + счётчик + сброс».
- **Data table** (https://carbondesignsystem.com/components/data-table/usage/) — пять плотностей строк (от extra small ~24px до extra large ~64px; актуальная норма для читаемых данных — medium/large ~40–48px, compact — для максимума строк на экран); **toolbar** над таблицей как единое место для поиска (сворачиваемого в иконку или постоянно открытого), фильтров и действий; сортировка с правилом «иконка сортировки видна только у отсортированной колонки, у остальных — по hover»; expandable rows для постепенного раскрытия. Для таблицы 43: toolbar-строка фильтров + переключатель плотности (обычная/компактная) + карбоновская логика сортировочных иконок.
- **Tag** (https://carbondesignsystem.com/components/tag/usage/) — четыре типа: read-only (категоризация), **dismissible** (удаляемые — «typically used for filtering», т.е. ровно наши активные фильтры-метки с ×), selectable (теги-переключатели фильтров), operational (раскрывают overflow — «+3 ещё»). Правила: тег — не ссылка навигации; цвет помогает различать категории, но не должен быть единственным носителем смысла — что совпадает с нашим правилом «статусный цвет только с текстовой меткой».
- **Content switcher** (https://carbondesignsystem.com/components/content-switcher/usage/) — сегментированный переключатель «двух и более секций контента в одном пространстве», всегда ровно один выбран, первый — по умолчанию; ярлыки — 1–3 слова-существительные, равная ширина сегментов. Отличие от вкладок: вкладки — «ящики картотеки» с разными областями, switcher — разные представления одного и того же. У нас: 4 раздела карточки мероприятия (паспорт / анализ / предложения / связи) — это content switcher, а не tabs; также подходит для переключения «таблица 43 / новая карта 30» и для выбора плотности таблицы.

### Что НЕ подходит и почему

Фирменный хром IBM: чёрный UI Shell (глобальный header), «поле-на-сером» стиль инпутов (field-01 на layer), синий #0f62fe (у нас свой #1E4FA3), резкие фокус-рамки 2px, dark-темы, а также тяжёлые части data table — batch actions с чекбоксами и пагинация (43 строки показываем целиком, отбор — фильтрами).

### Воспроизводимость средствами Tailwind + свои компоненты

Да. Строка фильтров — flex-toolbar: `input` поиска со значком, 2–3 кастомных dropdown (button + popover на `useState`/`useRef` c закрытием по клику вне и Escape), кнопка «Все фильтры» с бейджем-счётчиком `bg-[var(--ic-accent)] text-white rounded-full`; активные метки — `inline-flex items-center gap-1 rounded-full border border-[var(--ic-border)] px-2.5 py-0.5 text-sm` с кнопкой ×; «Сбросить всё» — текстовая кнопка. Плотность таблицы — проп `density: 'normal' | 'compact'` → `py-3/py-1.5`. Content switcher — контейнер `inline-flex rounded-lg border border-[var(--ic-border)] bg-[var(--ic-bg)] p-0.5`, активный сегмент `bg-white shadow-sm text-[var(--ic-accent)]`, роль `radiogroup`/`tablist` с клавиатурными стрелками.

### Нужна ли зависимость

Нет. `@carbon/react` тянет сотни килобайт стилей и собственную тему — нам нужны только правила паттерна фильтрации, шкала плотностей и логика компонентов, которые естественно выражаются в Tailwind-утилитах.

### Риск конфликта с текущим стилем

Самый низкий из четырёх по типографике (общий IBM Plex), но самый высокий по соблазну скопировать визуал (чёрный header, синий IBM, серые поля). Правило защиты: из Carbon берём размеры, плотности и поведение; все цвета — строго из `--ic-*`, поверхности остаются белыми со светлыми границами `#DDE1E7`.

### Итоговая рекомендация

Carbon — главный донор для строки фильтров (filtering pattern целиком: instant-фильтрация, счётчик на «Все фильтры», dismissible-теги, общий сброс), плотностей таблицы и content switcher для 4 разделов карточки. Родство по IBM Plex делает перенос пропорций почти бесшовным — при жёстком запрете на цвета и хром IBM.
